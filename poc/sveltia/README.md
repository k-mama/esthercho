# Sveltia CMS — Sprint 0 Proof of Concept

Status: TECHNICAL SCHEMA/UI POC — NOT SELECTED FOR PRODUCTION

This folder is intentionally isolated from the production Next.js application.

## What this PoC tests

The test configuration asks whether one non-developer editing surface can express:

- immutable Story identity generated by the system,
- shared archival metadata,
- independent KO/EN publication states,
- independent KO/EN titles, URL slugs, introductions, summaries, and bodies,
- one language remaining `not-started` while the other is published,
- photo upload with approximate year / people / consent question / locale caption,
- one Story entry rather than separate developer-managed metadata/body screens.

## Test backend

`admin/config.yml` currently uses:

```yaml
backend:
  name: test-repo
```

Sveltia's official Test backend stores content/assets in a browser-local virtual filesystem. It is appropriate for schema/UI exploration because it cannot push production content.

This means the current PoC is safe to inspect without connecting GitHub credentials.

## Local UI

The admin shell follows Sveltia's documented static installation pattern and loads the CMS bundle from:

`https://unpkg.com/@sveltia/cms/dist/sveltia-cms.js`

Serve the `poc/sveltia` directory through an HTTP server and open the admin page in a modern browser to inspect the form.

The production site does not expose this PoC path.

## Important official-architecture finding

Sveltia's deployed GitHub editing flow is not truly authentication-server-free for a non-technical editor.

A personal access token can be used directly, but the official GitHub backend documentation recommends OAuth for non-technical users. Authorization Code Flow requires an OAuth client server. Sveltia provides an authenticator that can run on Cloudflare Workers, Vercel, Netlify, or similar infrastructure.

Therefore a realistic production Sveltia architecture for this project would be conceptually:

```text
static Esther site + static Sveltia admin
              |
              v
small OAuth authenticator (likely Cloudflare Worker)
              |
              v
GitHub repository
              |
              v
Cloudflare Pages rebuild
```

That additional Worker/authenticator is an operational dependency and must be included in the CMS decision rather than hidden by the phrase “client-side CMS.”

## i18n observation

The PoC uses Sveltia's `multiple_files` i18n structure with KO and EN as independently editable locale values.

Shared Story metadata uses `i18n: duplicate` while language-owned fields use `i18n: true`.

The PoC deliberately creates both locale states so publication state remains explicit data rather than being inferred from whether a file happens to exist.

## Story ID observation

Sveltia has a read-only UUID field that can generate identity without Esther typing or editing it.

This is promising for author UX.

The PoC uses the generated Story ID as a stable storage slug while retaining separate locale-owned public URL slug fields. This is a PoC choice, not a ratified physical-file decision.

## Known PoC weakness

The embedded `photos` list is optimized for testing Esther's one-screen workflow, not for the final canonical media registry.

In production, a photo upload would need an ingestion layer that creates/links a durable Media record behind the same simple author questions.

Do not migrate this list schema directly into production merely because the UI feels convenient.

## Production decision still blocked on

- real author usability test,
- OAuth/Worker setup and recovery ownership,
- shared-field divergence behavior under `multiple_files`,
- media-registry integration design,
- validation/error UX,
- actual GitHub commit/deployment feedback to Esther,
- comparison with Keystatic's richer typed schema but heavier server requirement,
- Sveltia beta maintenance risk.

## Human acceptance task

Before Sveltia can be selected, Esther must be able to complete this without developer help:

1. create a Story,
2. write only the Korean original,
3. add several photos and captions,
4. leave the English original not-started,
5. save/publish through the configured Git workflow,
6. later reopen the same Story and add the English original,
7. understand whether the site deployment succeeded.

The current test-backend PoC validates schema/UI feasibility only. It does not yet satisfy this human acceptance test.
